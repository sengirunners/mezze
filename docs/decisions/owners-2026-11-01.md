# Owner namespaces, GitHub sign-in and join (design, 2026-11-01; decided 2026-11-02)

Status: **decided** (2026-11-02). Owners are GitHub accounts and sign-in is GitHub's; a join is plug and play, tied
to GitHub, with no join codes; the network is the host's own Tailscale. The authority runs the device flow, and a
renamed owner's old paths keep resolving. Build order: Q10. Stage 4 of [identifiers-2026-11-01.md](identifiers-2026-11-01.md).

## The problem

Today every name is local to one authority, and so is every person:

- A project is a ULID plus a slug (`harbor`). Slugs are unique per machine. A replica cannot join two projects
  with the same slug from two authorities: SPEC 17.4 says to rename one and join again.
- An identity is a ULID plus a name (`ivo`) per authority. The same person is a different identity on each
  authority, and joining one means an owner hands over a join code.
- A native issue id carries its project's prefix (`harbor-k4x`). The prefix is unique per authority only.
- Authorities move (zm remotes), so no reference may name a host.

People need one login, one reference that survives renames, transfers and authority moves, and a join that is
plug and play: the owner names a GitHub handle, the person runs one command.

## Layers

| thing | source of truth (never changes, never reused) | name (editable, display and lookup) |
| --- | --- | --- |
| owner (a GitHub user or org) | GitHub's **numeric account id** (`/user.id`) | the GitHub login: `ivo`, `example-org` |
| project | ULID (as today), plus a short handle `p4hw8tzk` (Q10 step 9) | `harbor`, unique under its owner |
| issue | ULID | prefix + random part, `harbor-k4x` (stage 1); title |

Project handles use stage 1's alphabet (`a-z 2-9` without `0 1 i l o`, at least one letter, the blocklist).
31^8 is 8.5e11, so an 8-symbol handle minted with no registry collides with odds below 1 in 1,000 until about
850 million exist.

A **reference** has two spellings: **by name**, `@ivo/harbor`, `@ivo/harbor/k4x` (an issue in the
project's native issues; Q7); and **by handle**, the permalink `zm:p4hw8tzk/k4x`, which never changes. Every
surface that takes a name resolves it once and stores the handle (the project's ULID until step 9). Text written
by a person keeps what they typed; links and structured fields keep the handle.

## The rule: a name is never rebound

**A name, once bound, stays bound to the same thing for ever.** Renames, transfers, suspensions and inactivity
never move a binding to something else. They can only add a new name for the same thing, or **freeze** it (it
then resolves read-only). `@ivo/harbor` in an old mail, README or doc reaches the project it reached when it
was written, or nothing; never a newcomer's project. GitHub's "redirect until the name is reused" is the hole
this closes (repo-jacking).

- **Owners are bound by id.** Every binding stores the GitHub id, never the login. A GitHub rename keeps every
  binding: zm re-resolves the login to the id.
- **Project names are bound by `(owner id, name)`**: `owner_names(owner, name, project, bound_at, current)`,
  primary key `(owner, name)`; triggers refuse any `UPDATE` of the key or the project and any `DELETE`.
- **Typed paths are pinned.** `login_paths(login, name) -> owner id` records every `@login/name` the authority
  bound or answered, append-only. Resolving `@login/name` follows the pin when there is one: to the pinned
  owner's binding, whoever holds the login on GitHub now. So when Ivo renames `ivo` to `iv` and GitHub
  later gives `ivo` to a newcomer, `@ivo/harbor` still reaches Ivo's project (`moved: @iv/harbor`),
  and the newcomer cannot bind `@ivo/harbor` (`conflict`). A path never answered before goes to the login's
  current holder, and is pinned from then on (answering `withdrawn` there would break the renamed owner's own
  links).
- **A login GitHub no longer answers** (renamed away, not yet reassigned) redirects one hop to its last id.
- A property test runs random binds, renames, transfers, GitHub renames, login reassignments, suspensions and
  cache expiry, and checks that every `@login/name` ever answered with a project keeps answering that project.
- **The cost, stated:** a project name used under an owner is gone for that owner's other projects, and a path
  this authority ever answered is gone for a later holder of that login.

## Decisions

### Q1. Who keeps the list of names? (decided: GitHub handles)

- `@owner` is a GitHub user or org, bound to its immutable numeric account id; the login is display and lookup
  only. Projects are `@owner/project` under that owner.
- **The directory is a brick** (`internal/owners`): an `Accounts` interface (who holds a token, an account by
  login, by id, org membership). v1's driver is GitHub, with configurable API and web base URLs (tests use a fake
  on httptest; GitHub Enterprise its own host); GitLab or local names can be other drivers later, behind the same
  conformance suite. Ids are namespaced by driver (`github:12345`). Project names live in **each authority's own
  project registry**. **No directory service run by the project in v1**, so no global name lookup.
- GitHub endpoints: `GET /user`, `GET /users/{username}`, `GET /user/{account_id}` (GitHub's documented "Get a
  user using their ID", docs.github.com/en/rest/users/users#get-a-user-using-their-id), `GET
  /user/memberships/orgs/{org}`.

### Q2. One login (decided: Sign in with GitHub, for people; the authority runs the flow)

- **The authority runs GitHub's OAuth device flow itself**, so no client ever handles a GitHub token:
  1. The CLI asks the authority to start a login (`POST /v0/login/github/start` with its purpose, link or bind;
     a join starts at `POST /v0/join/github`, Q11).
  2. The authority asks GitHub for a device code with zm's OAuth client id, scopes `read:user read:org`, and
     answers the CLI with the user code, the verification URL, a pending id and a poll secret (at least 128 bits
     from `crypto/rand`; the authority keeps only its hash).
  3. The person approves in the browser (`github.com/login/device`).
  4. The authority polls GitHub, receives the token directly, calls `GET /user` (and the org memberships the
     purpose needs), keeps only what it learned (the numeric id, the login, which orgs the person is an active
     member of), and discards the token: never stored, logged or echoed.
  5. The CLI polls the authority with the pending id and the secret (`POST /v0/login/github/{id}`, long poll).
     **The authority acts only when the outcome is collected**: it links, mints the member token, or binds then,
     and answers the result once. An outcome nobody collects expires (2 minutes after GitHub answered, or with
     GitHub's 15-minute code) with nothing created. The login is bound to the request that started it (the same
     identity for link and bind, the same node for join).
  Because the token comes from GitHub to the authority on zm's own device-code exchange, it is a token for zm's
  OAuth app (no PAT, no other app's token), and a captured outcome cannot be replayed at another authority. The
  device flow needs only the client id, **no client secret** (the app must have "Enable Device Flow" set); the
  client id is the authority's config (`github.client_id`, with `github.api_url`, `github.web_url`).
- **Device-code phishing, stated.** An attacker can run `zm login github` or `zm join harbor` and talk Bea
  into entering the attacker's user code. Then:
  - **Blast radius:** a join gives the attacker's node a member token with Bea's GitHub grant's role, in that
    project or area, revocable (`zm token revoke`, `zm identity unlink github --revoke`); a link links the
    attacker's identity to Bea's id, which would lock Bea out until an unlink (above).
  - **Owners see it:** the first link of an account, and every join from a node new to that identity, mails the
    identity itself (`human:<name>`) and the project's owners (`owners`) in each project concerned, naming the
    GitHub login, the identity, the node (name, stable id, tailnet login) and how to undo it.
  - **Bea sees who asks:** GitHub's device page shows only the OAuth app's name and the code; zm cannot add
    text there. The CLI prints which authority and node is asking next to the code ("authority mini asks
    GitHub to sign in beas-mac (nBEA...)"), and operators name the OAuth app after the authority ("zm on
    mini"). A person enters a code only from their own terminal.
- **No token on stdin in v1.** An existing `gh auth token` would be a token of GitHub CLI's app; accepting one
  safely needs `POST /applications/{client_id}/token` with a client secret from the Secrets brick. Not built;
  revisit if the device flow proves a burden.
- **Linking is explicit and once.** The authority maps a GitHub id to one zm identity: by `zm login github` from
  an identity that is already the whole person (the socket owner, or a replica's node-bound token; never a
  minted token, which is capped and would become a full login), or by a GitHub join (Q11), which creates or finds
  the identity linked to that id. An email match never links or merges. An identity linked to one id refuses
  another, and an id linked to one identity refuses a second (`conflict`) until it is unlinked.
- **Unlink and relink.** `zm identity unlink github <identity>`, by the machine owner on the socket or an admin
  of a project the identity holds a grant in, removes the link (and with `--revoke`, that identity's node-bound
  tokens). The GitHub user then relinks with a fresh device flow (`zm login github` from their own identity, or
  `zm join`), which takes the account over from the unlinked or compromised identity.
- **Machines and agents** (servers, CI, bots) keep zm's own invite and token flow, with no GitHub
  requirement. Agents are never owners.
- On a replica, `zm login github` and `zm names bind` start their login at the project's authority through the
  team proxy (the replica's node-bound token), so the authority still runs the flow.
- The pattern: numeric `/user.id` as the uid, no silent email merge, an explicit link.

### Q3. Name grammar and reserved names

- **Owner names** are GitHub's: logins compare case-insensitively (zm folds them for lookup, shows GitHub's case).
- **Project names** are `ValidSlug`, at least 2 characters, no blocked word (whole words). Reserved under every
  owner: `none all owners admin root system api www app web help support security abuse status settings new
  explore search login logout signup join invite`, and any name starting `zm-` (`api.ValidProjectName`).

### Q4. Squatting and disputes (decided: GitHub's)

- Owner names, squatting, trademark and impersonation are GitHub's process. No claim step, no named human, no
  human gate.
- **zm's only rule:** when GitHub reports the account suspended or deleted (`GET /user/{account_id}` answers
  404), that owner's names **freeze**: they resolve read-only (`frozen`), and nothing is bound, renamed or
  transferred under that owner, nor is a project whose current name is under it moved away. zm checks at every
  bind and when a resolve finds its owner record older than 1 hour; the freeze lifts when GitHub answers for the
  id again (the same id: nothing rebinds).

### Q5. Transfers

- A project moves to another owner by a bind under the new owner, by an admin of the project who proves the new
  owner (Q8). The old `(owner, name)` stays bound for ever (`moved: @new/harbor`).
- The project keeps its ULID, handle, prefix, issue ids and authority. A name the new owner already bound is
  refused.

### Q6. Renames

- **Project rename**: a new binding to the same project; the old name answers `moved`. Renaming back is allowed.
- **Owner rename** is GitHub's; zm re-resolves the login to the id, and pinned paths keep resolving (the rule).

### Q7. Prefixes (unchanged)

The prefix stays a per-authority display and routing key; the project's global identity is its handle (and
`@owner/name`). Prefixes may repeat across authorities, are fixed at creation, and travel with the project (a
move to an authority where it is taken is refused, with a hint to pick a destination prefix for new issues
only). `@owner/project/k4x` and `zm:<handle>/k4x` mean the **native** prefix; a tracker item needs its full work
id (`@owner/project/bd:solver-3x`).

### Q8. Private projects (decided: never listed anywhere public)

- There is no public list of projects (no directory service). Resolving `@owner/name` for a caller without read
  on the project answers exactly like a missing name.
- Only the owner (the GitHub id the authority just verified is the owner's) or an **admin of the owning org**
  (`/user/memberships/orgs/{org}`, state `active`, role `admin`, checked live with the binder's token during that
  login, never cached) may bind a name under `@owner`; an org member who is not an admin may not (names are never
  rebound, so one member, or one compromised account, could otherwise spend `@org/<name>` for good). A name collides only with the owner's own projects, reported at bind time
  (`conflict`).
- The binder must also be an admin of the zm project being named, and the GitHub account
  that approved must be the one linked to the binder's identity.

### Q9. Resolution, caching and offline

- **Resolve `@owner/name`**: the pin for `(login, name)` if any; else the login's current GitHub holder
  (`/users/{login}`, cached 1 hour; a login GitHub no longer answers redirects one hop to its last id), then
  `owner_names(id, name)`. Answers: the project, its current `@owner/name`, `moved`, `frozen`; or not found.
- **Caching.** Owner records `(id, login, kind, checked, gone)`, re-checked after 1 hour. With GitHub
  unreachable, cached owners resolve; an owner never seen is `unavailable`. GitHub allows 60 unauthenticated
  calls an hour per address; an authority may set its own lookup token (`github.lookup_token`, a secret
  reference), used only for lookups by login and id.
- A replica offline resolves its joined projects by name from its copy. Cross-authority permalinks (signed
  location records, project keys) and cross-authority mail (`human:@ivo`) are not in this stage; the first
  draft's location-record design stays the plan for them.

### Q11. Join by GitHub (decided: plug and play, no join codes)

- **Grants by GitHub handle or org.** On the authority, `zm grant @beagh owner harbor` resolves the login
  to its numeric id through the API at grant time and stores a **GitHub grant** `(account, project, area, role)`
  keyed to the id (a later rename of `beagh` keeps it). `zm grant @example-org member harbor` grants an org:
  its members qualify, checked live at join. `zm revoke @beagh harbor` removes one and what it gave (the
  grants rows and node-bound tokens of each join it admitted); `zm grants` lists them with the logins. No
  identity exists until the person joins.
- **Org members are re-checked** after the person's token is gone, hourly, with `github.lookup_token`: a secret
  reference (the Secrets brick; never the token in config.json) to an org member's token with scope `read:org`
  only, needed only once an org grant exists (`zm grant @org` refuses without it, saying so). Only what GitHub
  positively reports as ended removes an admission; a check that cannot run (expired, revoked, rate limited)
  removes nobody, mails the project's owners once, and after 24 hours of failures stops new joins through org
  grants until a check runs again. **Later, not v1:** a zm GitHub App installed in the org with `members:read`
  (installation tokens, nothing personal stored) replaces the lookup token.
- **`zm join <project>`** (no code), on the person's machine:
  1. The daemon finds the authority among its tailnet peers: each peer that runs zm (`:7433`) is asked `GET
     /v0/join/github`, which answers only "a zm authority, protocol v0" and its machine name: no project input,
     no project list, so it is no oracle for which projects exist. Several authorities: the daemon asks which
     (`--from <machine>`), a single one is used.
  2. It starts a GitHub login at that authority (`POST /v0/join/github`: the project as typed, the machine name),
     shows the user code, the URL and who is asking, and waits. The authority starts the device flow for any
     project name, known or not.
  3. When the outcome is collected (Q2), the authority takes the strongest role among the id's GitHub grants and
     the grants of orgs it is an active member of, for that project or one of its areas. **Unknown project, a
     project with no GitHub grants, and no grant for this account all answer one byte-identical refusal**, after
     the device flow, so a stranger learns nothing before approving and nothing after (a test compares them).
  4. It finds the identity linked to the id, or creates one named after the login (a taken name gets `-2`, `-3`;
     a name match never links), links it, adds the grant, and mints a **node-bound token** for the caller's
     node (the same node that started the login), exactly as invite redemption does (machine-name rules,
     `team_nodes`, scope_version). The daemon writes the token file and saves the remote as `zm join <code>`
     does today; bd, mail and work then go to the authority.
- **Trust in the authority** comes from the tailnet: the answering node's identity (WhoIs on the peer) is pinned
  on first join, as a join code's fingerprint pins it today.
- Invites and join codes stay, for machines, agents and anyone without GitHub.

### Q12. Network reach (decided: the host's own Tailscale; zm mints no keys)

- **The team owner adds a person through Tailscale's admin UI**: invite them to the tailnet, or share the
  authority's node with them. They install the Tailscale app and log in (GitHub works there too). zm mints no
  Tailscale keys and needs no Tailscale API key.
- **zm uses the host's Tailscale when it can.** When the machine runs Tailscale and reaches the authority over
  the OS network (its MagicDNS name, or the tailnet IP stored with the remote), `zm join` and the daemon dial
  that way; the authority's node is still pinned, by asking the host's tailscaled who answered (LocalAPI WhoIs on
  the connection's peer). **zm's embedded tsnet node is the fallback**, for headless boxes with an auth key (the
  headless flow today). The transport is pluggable: host network first, tsnet second.
- **The authority keeps one listener**, its tsnet node: a host-Tailscale machine on the same tailnet, or one the
  authority's node is shared with, reaches it as any peer, and the authority's WhoIs identifies the caller's host
  node, so node-bound tokens and every check stay as they are. Whether WhoIs answers for a node that reaches a
  *shared* node is checked by a real-tailnet test before step 7 ships; if it does not, sharing is documented as
  unsupported and the person is invited to the tailnet instead.
- **With the tunnel transport**: it adds `via: tailnet|tunnel`, where a
  tunnel member's "node" is its ed25519 key id (`zmkey:<fp>`). A GitHub join works over either: "the node that
  started the login" is the WhoIs stable node id over the tailnet and the signing key's `zmkey:` id over the
  tunnel, and the token binds to it as an invite's does. The transport work puts the transport behind one
  registered interface, `core.TeamTransport`, with drivers in `internal/tailnet` and `internal/tunnel` picked by
  `via`; host Tailscale is **a third driver** there.
- Remote-access alternatives considered and not taken: zm minting a short-lived Tailscale auth key per verified
  GitHub user (needs a Tailscale API key on the authority); a public HTTPS door (Cloudflare Tunnel, or
  Tailscale Funnel) with GitHub as the only gate.

### Q10. Order of work

Epic "zm: GitHub-backed owner names and sign-in"; one issue per step.

1. **This doc.**
2. **GitHub identity link**: the owners brick (`Accounts`, the GitHub driver, a fake GitHub,
   conformance); the authority-run device flow (`POST /v0/login/github/start`, `POST /v0/login/github/{id}`) with
   purpose link, acting on collection; `zm login github`; `zm identity unlink github`; the owner-visible mail.
   Tests: link, conflicts, unlink and relink, a non-person account, a minted token refused, a wrong poll secret,
   a collected outcome not collectable again, an uncollected one creating nothing, the secret's entropy, no
   token stored or printed.
3. **GitHub grants and join**: GitHub grants (`zm grant @handle|@org`, revoke, list), the
   discover route (no project input), the join purpose with its one uniform refusal, admission shared with
   invite redemption in the project registry, the join mail; `zm join <project>` with no code, and replicas
   forwarding `/v0/login/github/*` to the authority (team's proxy list).
4. **Host-network transport**: a third driver on `core.TeamTransport` (the transport follow-up):
   dial the authority over the host's Tailscale (MagicDNS or the stored IP, pinned through LocalAPI WhoIs), tsnet
   as fallback; the shared-node check. Built after that follow-up lands.
5. **A member joins, end to end**: a fake GitHub on httptest and a fake host network; the owner's
   authority runs `zm grant @beagh owner harbor`; the member's daemon runs `zm join harbor`, approves in the
   fake GitHub, gets a member token with no code, and bd, mail and work reach the authority.
6. **Owner namespaces**: names bound through the login flow (purpose bind), pinned paths,
   resolve, ls, the property test.
7. **Frozen owners** and the lookup token.
8. **Sign-in on a new machine**: folded into join (a linked identity joining from another
   machine is a join); closed into step 3.
9. **Project handles and `zm:` permalinks**: the stage 1 minter moves into `internal/ids`
   (with the issues owner); `zm:<handle>/k4x` resolves on an authority.

Later: cross-authority location records and keys, a GitLab driver, `gh` tokens verified by client secret.

Each step ships with tests per rule above; no test calls the live GitHub or a real tailnet.
